## 一、岗位分析与备考策略

> **岗位**：电商直播算法中心 · 推荐算法工程师
> **业务背景**：快手电商是公司核心增长曲线之一，直播带货是主战场。这个岗位的核心是为直播间/商品做实时推荐与排序。

### 直播推荐相比传统短视频推荐的三大独特挑战

1. **极强的实时性**：一场直播只持续几小时，item 的生命周期极短，召回库时刻在更新，传统离线训练-在线推理的范式完全跟不上。
2. **多模态内容理解**：直播是视频流+主播话术+商品信息+实时弹幕，多模态融合是基本盘。
3. **多目标融合极复杂**：观看时长、点击商品卡、下单、关注主播、点赞、评论、停留——目标之间冲突严重，需要在线动态融合。

### 快手在这个方向的核心论文（必须知道）

- **OneRec**（2025）：快手第一个端到端生成式推荐大模型，公司级落地
- **OneLive**（2025）：业界首个为直播场景设计的生成式推荐框架——**这就是你要面的部门相关的工作**
- **Pantheon**：快手直播排序的多目标融合方案，迭代帕累托优化

## 三、项目深挖：华为双塔召回系统

> 🎯 同美团版本，这是简历最硬核的一段。文稿、追问、数据卡完全沿用，但要补充一个**面向快手的迁移思考**。

### 📢 完整项目介绍文稿（约2分半，第一人称口语化）

好的，我介绍一下这个项目。

我在华为上海研究所实习的时候，负责 5G 基站的参数自动匹配系统。背景是这样的：基站出现异常后，工程师会提交一份 DTS 问题单描述故障，然后要从大约一万两千条 MO 参数里靠经验找出相关参数，再做发散测试定位根因。这个流程完全依赖个人经验，效率很低。我的任务就是把它自动化——本质上是一个信息检索问题：给定一条问题单，从一万两千条参数里召回最相关的那些。

我设计的是两路并行召回的架构。第一路是规则匹配，从问题单的 HTML 脚本字段抽取参数名关键词，用编辑距离匹配，每条单返回大约 15 条候选。这一路精度高，但只能抓到脚本里明文出现的参数名，对那种"上行带宽异常"这种语义化描述完全失效。所以我加了第二路——语义向量匹配，用一个微调过的双塔模型把问题单和参数描述编码到同一向量空间，余弦相似度检索 Top-50。两路互补：规则保精度，语义保覆盖。

整个项目我觉得最有意思的部分，是训练数据的构建。语义模型需要标注，但人工标一万多条参数成本太高，所以我设计了一个自动化闭环——把规则方法输出的"问题单-参数"配对直接当正样本用，从 80 条历史 DTS 单提取出了大约 500 个高质量正样本对。

难负例的挖掘也是全自动的。我用微调前的预训练模型对每条问题单检索 Top-20，把已经确认的正样本排除，剩下排名最高的 2 个就是最理想的难负例——它们恰好是预训练模型打高分、但实际不相关的混淆参数。比如一条"上行 EARFCN 异常"的问题单，模型可能把"下行 EARFCN 参数"排得很高，但它根本不是根因。这样我得到了大约 1000 个 Triplet。

训练上，预训练模型我选了 Paraphrase-multilingual-MiniLM——参数名英文、问题单中文需要跨语言对齐，而 MiniLM 参数量小延迟也可控。Triplet Loss margin 通过网格搜索定在 0.3，配合 Early Stopping。

效果上，我准备了 20 条精细标注的 DTS 单作为验证集，一共 130 个相关参数。纯规则基线的覆盖率只有 51.5%，加上语义召回之后，完整系统达到了 74.6%，差不多就是 75%。最后两路结果用一个三档优先级融合——双方都召回的最优、只规则次之、只语义最末，下游工程师按优先级依次发散测试就行。

### 🔄 面向快手的迁移思考（追问"这经历和直播推荐有什么关系"时用）

这段经历的方法论可以**直接迁移**到直播推荐召回：
1. **双塔结构** → 直播召回的 user-item 双塔
2. **难负例挖掘** → 直播召回中区分"主播相似但用户不感兴趣"和"真正不相关"的样本
3. **多路并行召回** → 直播场景标配（兴趣召回、热门召回、地理召回、协同召回等）
4. **小验证集 + 严格评测** → 直播场景因 item 时效性短，难以构建大验证集，这套方法论很贴近

### 高频追问 Q&A

**Q1：两路结果怎么融合的？**
> A：取并集合并。三档优先级规则——两路都召回的最可信排第一档；只有规则的排第二档（精确但覆盖窄）；只有语义的排第三档（覆盖长尾但噪声多）。下游发散测试成本高，按优先级依次跑。

**Q2：为什么用 Paraphrase-multilingual？**
> A：①参数名英文、问题单中文，需要跨语言语义对齐；②MiniLM 参数量小（66M）推理快，1 万+候选场景延迟可控。

**Q3：Triplet margin 怎么调的？**
> A：网格搜索试了 0.1/0.2/0.3/0.5。太小区分压力不够，太大训练不稳定。最终 0.3 + lr 2e-5 + batch 128 效果最好。

**Q4：失败 case 分析过吗？**
> A：分析过 2 个低覆盖率 case。一个描述极简短、缺语义信息（0%）；一个跨多子系统、参数分散（33%）。后者暴露了单向量表示对多意图查询的局限，可以用查询意图分解改进。

**Q5：和推荐系统/直播推荐有什么关系？**
> A：本质就是召回层。双塔结构、Triplet Loss、难负例采样在工业推荐里完全通用。直播场景下用户 query 是用户画像+实时上下文，候选是主播/商品，技术框架完全可迁移。

## 四、项目深挖：ReEnsemble（强化学习多模型集成）

> 🎯 强化学习经历是稀缺亮点，快手 OneRec 里也用了 RL 做 Preference Alignment，对口度高。

### 📢 完整项目介绍文稿（约90秒，第一人称口语化）

好的，这个项目叫 ReEnsemble，是我在密西根的一门高级机器学习课上的研究项目，核心是用强化学习做多模型集成。

任务是新闻文章的政治立场预测，三分类——左、中、右。我们先训了 BERT、BiLSTM、SVM 三个基础分类器，发现单模型的天花板都在 45% 左右，但传统集成方法都不太行——Stacking 的 Macro-F1 直接崩到 0.21，因为它退化成只预测多数类了。

我的核心 insight 是：不同的样本，最适合的融合方式其实不一样。有些文章 BERT 的语义理解更准，有些 LSTM 的序列模式更有效。所以我希望有一个机制，能根据每个样本本身的特点动态地决定信谁——这就是我引入强化学习的动机。

具体做法是：把三个基础模型输出的 logit 拼起来作为状态向量，让 Actor 输出一组连续的软权重，对模型输出做加权融合；奖励函数设计成 1 减去融合后的交叉熵 loss，是一个稠密奖励。算法上我选了 DDPG，因为权重是连续动作空间，DQN 用不上。

最后实验结果，ReEnsemble 在所有集成方法里 Macro-F1 是最高的，达到 0.4162，比最强的单模型 BERT 还略好，说明这种动态加权的思路确实有效。

这个项目其实和搜推系统高度相关——MMOE 里 Gate 网络按任务动态分配 Expert 权重，本质和我做的事一样；多路召回融合也是同样的场景。所以后来我学推荐系统的时候，对很多融合机制都能很快建立直觉。

### 实验数据速查

| 模型 | Accuracy | Macro-F1 |
|------|----------|----------|
| BERT | 0.4554 | 0.4195 |
| LSTM | 0.4438 | 0.3097 |
| SVM  | 0.4023 | 0.3574 |
| Stacking | 0.4608 | **0.2103** ← 失败 |
| Majority Vote | 0.4585 | 0.3856 |
| **ReEnsemble** | 0.4592 | **0.4162** ← 集成最高 |

### 高频追问 Q&A

**Q1：为什么用强化学习而不是 Stacking？**
> A：Stacking 是静态融合，所有样本一套权重。RL 能**逐样本动态加权**——有些样本 BERT 准、有些 LSTM 准。Actor 根据 logit 分布决定信谁。实验验证：Stacking Macro-F1 只有 0.21，ReEnsemble 0.42。

**Q2：为什么选 DDPG？**
> A：动作空间连续——Actor 输出 [w1,w2,w3] 软权重，DQN 类离散算法用不了。DDPG 专为连续动作空间设计。

**Q3：和 MMOE / 推荐系统的多任务/多塔融合有什么关系？**
> A：**思路高度相似**。MMOE 的 Gate 按任务动态分配 Expert 权重，本质也是"按输入决定信谁"。区别是 MMOE 用监督学习训 Gate，我用 RL。**多路召回融合**也是同样的场景——不同召回路分数量纲不一致，可以用类似方法动态加权。这说明我对模型融合有跨场景的理解。

**Q4：和快手 OneRec 的 Preference Alignment 有什么相似？**
> A：OneRec 用迭代偏好对齐（类似 RLHF）来 fine-tune 生成式推荐器，本质也是 RL 优化推荐目标。我做的是用 RL 做模型融合，OneRec 用 RL 做生成器对齐——**RL 在推荐场景的应用是相通的**：传统监督学习只能优化离散点击信号，RL 能直接优化更复杂的、和业务目标对齐的奖励函数。

## 五、新增亮点：TIGER 复现与生成式推荐学习

> 🎯 这是你这次面试的**核心王牌**。一定要主动、详细地讲，直接拉满印象分。

### 📢 完整介绍文稿（约2分半，第一人称口语化）

好的，这是我最近投入精力最多的一个项目，也是我特别想跟您聊一聊的。

大概一个月前我开始系统学习生成式推荐方向，读完几篇代表性论文之后，决定亲手把 TIGER 复现一遍。TIGER 是 Google 2023 年的工作，是这条技术路线的开山之作——把它跑通，就等于理解了 OneRec、OneLive 这一系列后续工作的底层原理。我没有直接复现 OneRec，是因为它规模太大、个人复现成本不现实。选 TIGER 是为了用最小的代价跑通最核心的技术链路。

TIGER 的核心思路是把推荐重新建模成序列生成。分两步走：第一步用 RQ-VAE 把每个 item 的内容 embedding 离散化成一个长度为 K 的 token 序列，叫做 Semantic ID；第二步把用户的历史行为序列——其实就是一串 Semantic ID——喂给 Transformer Decoder，让它自回归地生成下一个 item 的 Semantic ID。本质就是把推荐变成一个 seq2seq 问题。

我在 MovieLens 上跑通了完整流程，最棘手的问题是 codebook collapse——RQ-VAE 训练初期由于初始化和梯度更新不均衡，一些 codeword 长期没有 input 落在它们附近，梯度一直是 0，慢慢就"死掉"了，整个 codebook 的有效容量远远小于设计容量。我用了两个方法解决：一是用 EMA 更新代替直接梯度更新，这是 VQ-VAE 系列的标准做法；二是 dead code reset——每个 epoch 结束统计一遍 codeword 的使用频率，把使用率低于阈值的直接替换成高频 codeword 加扰动，相当于让活跃区域复制一份去占领新空间。这一改之后 codebook 利用率有了明显提升。

另一个让我印象很深的细节是推理时的合法性约束。Beam search 默认是按 token 概率自由扩展的，但并不是所有 token 组合都对应真实 item——不加约束的话 beam 会浪费在无效组合上。我的解法是把所有真实 item 的 Semantic ID 建成一棵 prefix tree，beam search 每一步只允许扩展 trie 里存在的子节点，召回率显著提升。

最后 Recall@10 达到了和论文相当的水平。但对我来说更重要的不是这个数字，而是这次复现让我对生成式推荐的几个核心问题——tokenization 质量、暴露偏差、合法性约束——都有了直接的工程体感，而不是停留在论文层面。这也是我特别想加入快手、在这个方向继续深入做下去的原因。

### 🔥 预测追问 & 标准答案

**Q1：为什么选择 TIGER 而不是直接复现 OneRec？**
> A：两个原因。①TIGER 是这条技术路线的"开山之作"，把它跑通，就理解了 OneRec、OneLive 这一系列工作的底层原理；②OneRec 是工业级模型，规模和数据要求都很高，个人复现成本不现实。我选择 TIGER 是希望以最小代价跑通**最核心的技术链路**，再去读 OneRec 时就能真正读懂每一个技术细节。

**Q2：codebook collapse 的本质是什么？你怎么解决的？**
> A：本质是 RQ-VAE 训练过程中，由于初始化和梯度更新不均衡，某些 codeword 长期没有 input 落在其附近，导致它们的梯度永远是 0，逐渐"死掉"——最终 codebook 的有效容量远小于设计容量。
>
> 我用了两个方法：①**EMA 更新**而不是直接梯度更新（Vector Quantization 的标准做法）；②**dead code reset**：每个 epoch 结束统计 codeword 使用频率，把使用频率低于阈值的 codeword 替换成被高频使用的 codeword 加上一个小扰动，相当于把"活跃区域"的 codeword 复制一份让它去"占领"新的空间。

**Q3：自回归生成有暴露偏差（exposure bias）问题，你怎么处理？**
> A：暴露偏差指**训练时**用 ground truth 做 teacher forcing，**推理时**用模型自己生成的结果作为下一步输入，分布不一致。我在复现里没有专门处理（因为效果已经够用），但论文里有几种方法可以借鉴：①**Scheduled Sampling**：训练时按一定概率用模型自己的预测代替 ground truth；②**Beam Search 训练**：训练阶段就引入 beam search 让模型见过自己的输出。

**Q4：推理时怎么保证生成的 token 序列对应合法的 item？**
> A：用 **prefix tree（trie）约束 beam search**。把 codebook 里所有真实 item 的 Semantic ID 序列建成一棵字典树，beam search 每一步只允许扩展 trie 中存在的子节点。这样不会浪费 beam 在无效组合上，召回率能显著提升。

**Q5：TIGER vs HSTU vs OneRec，怎么对比？**
> A：三者代表了生成式推荐的三种思路：
> - **TIGER** (Google)：用 RQ-VAE 做 item tokenization + Transformer 自回归生成。**核心创新是 Semantic ID**，让生成式范式可行。
> - **HSTU** (Meta)：保留传统的 ID Embedding，但用一个新型的 Hierarchical Sequential Transducer Unit 取代标准 Attention，重点是**做 scaling**，让推荐模型能像 LLM 一样从 scale 里受益。
> - **OneRec** (Kuaishou)：把召回和排序统一成一个 Encoder-Decoder 生成模型，**重点是工业级落地**——MoE 架构降本、Preference Alignment 对齐目标、整个系统替换传统多级漏斗。
>
> 一句话总结：**TIGER 解决"怎么生成"，HSTU 解决"怎么 scale"，OneRec 解决"怎么落地"**。

**Q6：HLLM 又是什么？**
> A：HLLM 是字节的工作，**Hierarchical LLM for Recommendation**。核心思想是用两层 LLM——下层 Item LLM 负责理解 item 的文本描述生成 item embedding，上层 User LLM 负责建模 user 的行为序列。它的特点是**完全基于文本**，不依赖任何离散 ID，所以天然适合冷启动和跨域迁移。和 TIGER/OneRec 走的"离散化"路线形成鲜明对比。

**Q7：你觉得生成式推荐的最大瓶颈是什么？**
> A：我个人觉得有三个：
> 1. **Tokenization 质量**：item embedding 怎么离散化得好，直接决定了下游生成质量。RQ-VAE 是当前主流但远没解决。
> 2. **冷启动 item**：新 item 没有 Semantic ID，需要在线快速生成，但 RQ-VAE 训练和推理是分离的。
> 3. **多目标优化**：生成式范式天然是单目标的（next token prediction），怎么把 CTR/CVR/时长等多个目标融入生成过程是开放问题。OneRec 用 Preference Alignment 是一个解法但不是终极方案。

## 六、生成式推荐核心论文速记

> 🎯 这是面试官最可能展开追问的区域。每篇都按"一句话核心 + 关键技术 + 影响"的格式背。

### TIGER (Google, 2023)
- **一句话：** 用 RQ-VAE 把 item 编码成 Semantic ID，再用 Transformer 自回归生成下一个 item 的 ID。
- **关键技术：** RQ-VAE (Residual Quantization VAE)、Semantic ID、Beam Search + Prefix Tree
- **影响：** 生成式推荐的奠基工作，证明了"生成范式"在推荐中可行。

### HSTU (Meta, 2024)
- **一句话：** 不做 tokenization，而是设计一个新型 Hierarchical Sequential Transducer Unit 替代标准 Attention，核心是**让推荐模型像 LLM 一样 scale**。
- **关键技术：** Pointwise aggregated attention（计算复杂度从 O(n²d) 降到接近线性）、相对位置编码、统一的"动作-item"序列建模
- **影响：** Meta 在自家 IG/Reels 落地，验证了推荐模型的 Scaling Law。

### HLLM (ByteDance, 2024)
- **一句话：** 用两层 LLM——Item LLM 理解 item 文本、User LLM 建模 user 序列——完全摆脱离散 ID。
- **关键技术：** Hierarchical LLM、纯文本表示、迁移学习友好
- **影响：** 冷启动和跨域推荐的新思路。

### OneRec (Kuaishou, 2025) ⭐ 必背
- **一句话：** 业界第一个工业级落地的端到端生成式推荐大模型，把召回+排序统一成一个 Encoder-Decoder。
- **关键技术：**
  - Encoder：MoE + 多模态 + 离散 token 序列
  - Decoder：自回归生成 item Semantic ID
  - **Iterative Preference Alignment**：类似 RLHF，用奖励模型对齐业务目标
  - LogQ Debiasing：修正流行度偏差
- **效果：** 训练/推理 MFU 提升到 23.7%/28.8%，OPEX 降到传统方案的 10.6%。
- **意义：** 标志着推荐系统从"多级漏斗"走向"端到端大模型"的范式变革。

### OneLive (Kuaishou, 2025) ⭐⭐ 你要面的部门相关，必背
- **一句话：** 业界第一个为**直播场景**设计的动态统一生成式推荐框架。
- **核心挑战：** 直播 item 生命周期短（几小时）、内容动态演化、实时性要求严苛。
- **关键技术：** 动态内容理解（滑动窗口 + 长期池化）、实时索引更新、统一生成式架构。
- **影响：** 在快手直播场景全量上线，直播搜索 CTR/CVR 取得历史性提升。
- **如何在面试中提：** "我特别关注 OneLive 这篇工作，因为它针对的就是电商直播算法中心要解决的核心问题。"

### SASRec (2018) — 经典基线
- **一句话：** 用 Self-Attention 对用户行为序列建模，预测下一个 item，是序列推荐的奠基工作。
- **关系：** 是 TIGER/HSTU 等所有生成式工作的"祖师爷"，要能讲清楚它和后续工作的演进关系。

## 七、八股 QA：召回与排序模型

### Q1：双塔模型的局限性？
**核心答：** 无法使用 user-item 交叉特征，训练和预测需保持塔分离，实时交互信号难利用。
**展开：** 解决方案是召回后加粗排层，或用 ColBERT 风格的 Late Interaction（每个 token Embedding 做最大相似度聚合）。

### Q2：MMOE 解决了什么？Gate 的作用？
**核心答：** 解决多任务学习的 seesaw problem。每个任务有独立 Gate 对多个 Expert 加权，让不同任务选择性利用不同专家。
**展开：** `output_k = Σ gate_k(x)[i] × expert_i(x)`。任务相关度中等时优于 Shared-Bottom；任务差异极大时用 PLE。

### Q3：DIN 的核心思想？
**核心答：** 用户兴趣是多样的，对历史行为做**目标感知的注意力加权**，而非简单 Pooling。
**展开：** `s_i = MLP([e_hist_i, e_target, e_hist_i - e_target, e_hist_i ⊙ e_target])`。

### Q4：负样本采样为什么重要？常见策略？
**核心答：** 召回模型在全库做检索，负样本必须覆盖全分布，不能只用曝光未点击（SSB 偏差）。
**策略：** 全局随机、热度加权 `P(i) ∝ freq(i)^0.75`、Batch 内负采样、Hard Negative Mining。

### Q5：多路召回结果如何融合？
**核心答：** 量纲不同不能直接比较。
1. **RRF（Reciprocal Rank Fusion）：** `score = Σ 1/(k + rank_i)`
2. **归一化加权求和**
3. **统一粗排打分**（最推荐）

### Q6：Position Bias 怎么解决？
**核心答：** 用户点击受位置影响，直接用日志训练会学到位置偏差。
**解决：** PAL（位置塔，推理时去掉）/ IPS 逆倾向加权 / 随机展示实验。

### Q7：SSB（样本选择偏差）问题？
**核心答：** CVR 模型只用"点击后是否转化"训练，但上线对全曝光打分，分布不匹配。
**解决：** ESMM 在全样本空间联合训练 pCTR 和 pCVR，`pCTCVR = pCTR × pCVR`。

### Q8：Transformer Self-Attention 复杂度及优化？
**核心答：** O(n²d)。
**优化：** Sparse Attention / Linear Attention / FlashAttention / SIM。

### Q9：ID Embedding 维度怎么选？
**核心答：** 经验公式 `dim ≈ min(50, cardinality^0.25 × c)`，常取 16~256。低频 ID 映射到 `<UNK>`。

### Q10：DPP 多样性算法？
**核心答：** 行列式点过程，用 Embedding 行列式（几何体积）度量多样性。工业上用贪心 DPP，复杂度 O(nk)。

## 八、八股 QA：直播推荐特有问题

> 🎯 这一节是为电商直播岗特别准备的，是你"我懂这个业务"的体现。

### Q1：直播推荐和短视频推荐最大的区别是什么？
**核心答：** 三点：
1. **Item 生命周期极短**——一场直播只有几小时，传统的离线训练-在线推理几乎跟不上，需要近实时的 item 表征更新。
2. **内容动态演化**——主播在不同时段讲不同商品，同一个直播间的"主题"会变化，要用滑动窗口持续生成"最新内容状态"向量。
3. **多目标更复杂**——除了点击和时长，还有下单、关注、加购、分享等强业务信号，多目标融合冲突更严重。

### Q2：直播间的实时召回怎么做？
**核心答：** 双层架构：
- **静态召回层**：基于直播间画像（主播标签、品类）做传统双塔召回，离线建好向量索引。
- **实时召回层**：基于"开播时间、当前讲解商品、实时人气、弹幕情绪"等流式信号做兴趣补充。
- 两层结果按时效性加权融合。

### Q3：怎么处理直播的冷启动？
**核心答：**
- **新直播间**：用主播历史画像 + 商品类目做初始 embedding，用 Bandit 探索分配少量流量
- **新主播**：用内容特征（封面图、标题、商品 SKU）做 content-based 召回
- **直播开播瞬间**：流量先用类目热门兜底，等积累 10-30 分钟用户反馈再切换到个性化召回

### Q4：直播多目标优化的难点？
**核心答：** 目标之间冲突严重——比如"长观看"和"快速下单"在某种程度上是矛盾的。常用方案：
1. **多任务学习**：MMOE/PLE 共享底层
2. **多目标融合公式**：`Score = pCTR^α × pVTR^β × pPay^γ`，α/β/γ 在线 AB 调
3. **快手 Pantheon 方案**：用迭代帕累托优化自动找到目标间的平衡点，不需要手工调权重

### Q5：直播场景下，生成式推荐的优势是什么？
**核心答：** 三个维度：
1. **端到端建模**：传统多级漏斗在直播场景下每一级都难以独立优化（数据稀疏、时效短）；端到端能让信号在召回-排序之间无损流动。
2. **多模态原生融合**：生成式架构（Encoder-Decoder）天然能处理多模态序列输入。
3. **快速适应新内容**：通过 in-context 信号让模型对新开播的直播间快速建立表征，不需要等离线训练。

OneLive 就是基于这三个动机设计的。

## 九、八股 QA：机器学习基础

### Q1：过拟合的原因与解决？
**原因：** 模型容量过大、数据不足、噪声多、特征冗余。
**解决：** L1/L2/Dropout、数据增强、Early Stopping、降低复杂度、集成。

### Q2：L1 vs L2 正则？
| | L1 | L2 |
|---|---|---|
| 惩罚 | `λΣ\|w\|` | `λΣw²` |
| 解 | **稀疏** | **平滑** |
| 用途 | 特征选择 | 防极端权重 |

### Q3：BN vs LN？
| | BN | LN |
|---|---|---|
| 归一化维度 | Batch 维 | 特征维 |
| 依赖 batch | 是 | 否 |
| 场景 | CV | NLP/推荐 |

### Q4：AUC 含义和局限？
**含义：** 正样本得分 > 负样本得分的概率（排序能力）。
**局限：** 不反映概率校准、对类别不平衡不敏感、可能被头部用户主导 → 用 **GAUC**（按用户分组算 AUC 再平均）。

### Q5：梯度消失/爆炸？
**解：** 残差连接、BN/LN、梯度裁剪、ReLU/GELU、LSTM 门控。

### Q6：Adam 为什么推荐系统常用？
**核心：** ID Embedding 稀疏，Adam 自适应学习率让低频特征也能合理更新。

### Q7：GBDT vs XGBoost vs LightGBM？
- **XGBoost = GBDT + 二阶导 + 正则化**
- **LightGBM = XGBoost + Leaf-wise 生长 + 直方图分裂**

### Q8：交叉熵 vs MSE？
**MSE 用于分类的问题：** Sigmoid + MSE 在饱和区梯度趋于 0，训练慢。
**交叉熵：** `∂L/∂z = ŷ - y`，梯度幅度与误差成正比。

### Q9：Transformer 为什么除以 √d_k？
**原因：** d_k 大时 Q·Kᵀ 方差大，softmax 进入饱和区。除以 √d_k 把方差归一化为 1。

### Q10：FTRL 是什么？
**核心：** 在线学习算法，结合 L1 稀疏性 + AdaGrad 自适应学习率，工业级推荐系统在线更新的标配。

### 必刷题（按出现频率排序）

#### 1. 数组中第 K 大的元素（你已经做过 ✅）
- LeetCode 215，**Medium**
- 三种解法都要会：排序 / 小根堆 / **QuickSelect O(n)**
- QuickSelect 是最优解，面试官如果追问"还有更优的吗"就要写出来

```python
def findKthLargest(nums, k):
    # 找第 k 大 = 找排序后第 (n-k) 小
    target = len(nums) - k
    def quickselect(l, r):
        pivot = nums[r]
        i = l
        for j in range(l, r):
            if nums[j] < pivot:
                nums[i], nums[j] = nums[j], nums[i]
                i += 1
        nums[i], nums[r] = nums[r], nums[i]
        if i == target: return nums[i]
        elif i < target: return quickselect(i+1, r)
        else: return quickselect(l, i-1)
    return quickselect(0, len(nums)-1)
# 平均 O(n)，最坏 O(n²)
```

#### 2. 手撕 Multi-Head Attention（高频，几乎必考）
```python
import numpy as np

def multi_head_attention(Q, K, V, num_heads):
    # Q, K, V: [batch, seq_len, d_model]
    batch, seq_len, d_model = Q.shape
    d_k = d_model // num_heads

    # 1. Linear projection 后 reshape 成多头
    Q = Q.reshape(batch, seq_len, num_heads, d_k).transpose(0, 2, 1, 3)
    K = K.reshape(batch, seq_len, num_heads, d_k).transpose(0, 2, 1, 3)
    V = V.reshape(batch, seq_len, num_heads, d_k).transpose(0, 2, 1, 3)

    # 2. Scaled dot-product attention
    scores = np.matmul(Q, K.transpose(0, 1, 3, 2)) / np.sqrt(d_k)
    weights = softmax(scores, axis=-1)
    output = np.matmul(weights, V)

    # 3. Concat heads
    output = output.transpose(0, 2, 1, 3).reshape(batch, seq_len, d_model)
    return output
```
